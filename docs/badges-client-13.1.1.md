# Бейджи: что клиент ждёт от сервера после порта exteraGram 13.1.1 («Ваши возможности»)

Ветка клиента `port/c-supporter`. Основа — контракт v1 (`/root/gramsrv/docs/badges.md` на sg).
Всё ниже выведено из smali exteraGram 13.1.1 (72379). Сервер должен повторить ровно эти формы.
Пока сервер новых полей не отдаёт, клиент работает как раньше: номер не показывается, кнопки передачи нет
(она включается ключом `sg_badges_transfer`, см. §3).

## 1. ProfileDTO: новое поле `number`

exteraGram 13.1.1 добавил в `ProfileDTO` **одно** поле (остальные «~10 членов» из diff — сгенерированные
Kotlin методы data-класса: `component8`, `copy`, `getNumber`, …):

| Поле | JSON-тип | Семантика |
|---|---|---|
| `number` | число (int32) или отсутствует / `null` | Порядковый номер значка поддержавшего. Показывается как `#N`. |

```json
{"id":1780244143,"type":"USER","status":"SUPPORTER","badge":{"documentId":6100000000000000001,"text":null},"canChangeBadge":false,"deleted":false,"number":6250}
```

Как клиент его использует (`BadgesController.getNumber`):

- номер виден только если `number > 0` **и** `status` = `SUPPORTER` или `DEVELOPER`; у `DEFAULT` (trusted, рамка без бейджа) игнорируется;
- `#N` гравируется на 3D-стрелке, рисуется пилюлей «Значок #N» (кастомный бейдж) и подсказкой над именем
  в профиле: «Стрелка #N» (стандартный) / «Значок #N» (кастомный, документ ≠ `sg_badges_default_document_id`);
- приветствие «Спасибо за поддержку!» прокатывает номер цифрами; «Ваши возможности» пишет «Значок #N — вот что вам доступно:».

Правило выдачи номера (как у exteraGram, номер приходит только с сервера, клиент его не считает):

- **последовательный, с 1**, в порядке первой выдачи платного бейджа (supporter или custom) пользователю;
- **постоянный**: апгрейд supporter → custom, смена эмодзи/подписи номер не меняют;
- **не переиспользуется**: после отзыва номер не выдаётся другому;
- **переезжает с бейджем** при передаче (см. §2) — у нового владельца тот же номер;
- developer: номер по желанию (клиент покажет, если есть); trusted / каналы — без номера;
- изменение номера должно поднимать `updated_at` строки (иначе не придёт в `profiles/updates`), и входить в ETag.

Клиент хранит его в колонке `number INTEGER` таблицы `ProfileDTO` (exteraGram: `MIGRATION_5_6`). При
появлении колонки клиент сбрасывает водяную метку и делает полный `GET profiles` — номера подтянутся сами.

Endpoint `GET profiles/{id}` (уже есть) теперь вызывается клиентом после передачи — должен отдавать тот же
ProfileDTO с `number`; `404` = бейджа нет.

## 2. Передача бейджа другому аккаунту

exteraGram делает это **inline-запросами к API-боту** (тот же механизм, что `badge <id> <text>`), без HTTP.
У нас бот — `sg_badges_bot` (@StaticBadgesBot). Ответ, как и для `badge`: одна статья, клиент читает
`results[0].send_message.message`, CacheTime 0.

Оба аккаунта залогинены на одном устройстве; клиент сам переключает, от чьего имени слать запрос.

### 2.1 `transfer_init` (от текущего владельца бейджа)

Запрос: inline-query `transfer_init` от аккаунта-источника.

Ответы:

| Строка | Значение |
|---|---|
| `token:<T>` | одноразовый токен передачи. `<T>` — непрозрачная строка без пробелов (до ~200 символов: весь inline-query `transfer_claim <T>` должен влезть в 256). |
| `cooldown:<unixtime>` | передача пока недоступна; `<unixtime>` — секунды UTC, когда станет можно. Клиент пишет «Следующая передача будет доступна **<дата>**». |
| любая другая (`error: …`) | «Не удалось передать значок. Попробуйте позже.» |

Проверки сервера: вызывающий — живой пользователь с бейджем `SUPPORTER` (не developer/trusted — клиент
таким кнопку не показывает, но сервер обязан отказать сам), кулдаун не активен. Токен:
привязан к источнику, одноразовый, короткий TTL (рекомендуем 5 минут). Повторный `transfer_init` выдаёт новый
и гасит прежний.

### 2.2 `transfer_claim <T>` (от аккаунта-получателя)

Запрос: inline-query `transfer_claim <T>` от аккаунта-получателя, сразу после 2.1.

| Строка | Значение |
|---|---|
| `ok` | бейдж перенесён. |
| `target_not_eligible` | у получателя уже есть бейдж (клиент: «У этого аккаунта уже есть значок»). |
| любая другая | «Не удалось передать значок. Попробуйте позже.» (просрочен/чужой/использованный токен, получатель = источник, бот/удалённый аккаунт и т. п.) |

Что делает сервер на `ok` (атомарно):

- строка бейджа (вид supporter/custom, документ, подпись, **номер**, `canChangeBadge`) переезжает к получателю;
- у источника — надгробие `deleted:true` (уйдёт в `profiles/updates`);
- оба `updated_at` растут, ETag меняется;
- ставится кулдаун **30 дней** на этот бейдж (текст подтверждения в клиенте: «следующая передача будет доступна через 30 дней»).
  exteraGram держит кулдаун на бейдже (номере), а не на аккаунте — рекомендуем так же;
- рамки аватара: права `frame_granted` не переносятся; стиль рамки у источника снимается, если без бейджа он больше
  не носим (как при отзыве), у получателя рамка не ставится — по решению владельца, клиент тут ничего не ждёт;
- журнал `badges.transfer` (кто, кому, номер).

После `ok` клиент зовёт `GET profiles/{источник}` и `GET profiles/{получатель}`, затем обычный sync.

### 2.3 Передача на аккаунт, которого нет на устройстве

Пункт «Другой аккаунт…» открывает `https://t.me/<sg_badges_bot>?start=transfer` (exteraGram:
`t.me/<api bot>?start=transfer`). Бот на `/start transfer` должен в чате провести тот же обмен:
выдать токен (или кнопку/ссылку `t.me/<bot>?start=claim_<T>`), которую получатель откроет со своего аккаунта.
Формат внутри чата клиент не разбирает — на усмотрение сервера.

## 3. App config

| Ключ | Тип | Что делает в клиенте |
|---|---|---|
| `sg_badges_early_builds_url` | строка, ссылка (`https://t.me/+…` или `https://t.me/<канал>`) | Канал ранних сборок для поддержавших (exteraGram: Firebase-ключ `supporters_channel_link`). Есть — строка «Ранние сборки» в «Ваших возможностях» кликабельна, основная кнопка «Канал ранних сборок». Нет/пусто — строка скрыта, кнопка «Понятно». Ссылка-приглашение видна только тем, кто открыл лист, т. е. поддержавшим. |

| `sg_badges_transfer` | bool (`true`/`false`, по умолчанию `false`) | Бот умеет `transfer_init`/`transfer_claim` (§2). Пока `false` — кнопок «Передать другому аккаунту» (в «Ваших возможностях») и «Передать» (в листе редактирования) нет. Своего аналога у exteraGram нет — там передача есть всегда. |

Остальные ключи без изменений; лист «Как получить» у чужого бейджа использует `sg_badges_shop_url`,
`sg_badges_price_supporter`, `sg_badges_price_custom`.

## 4. Что exteraGram ещё делает и чего у нас нет

- **«Сейчас играет» (Last.fm / stats.fm) и «Даты регистрации»** — перки exteraGram; у нас их нет, в списке
  перков (`SupporterPerks.PERKS`) они не показываются. Новые перки добавляются строкой в этот список.
- **BotCloudStorage `supporter_welcome`**: exteraGram помечает «приветствие показано» в облачном хранилище API-бота,
  чтобы не повторять на других устройствах. У нас хранилища бота нет — отметка только локальная
  (`supporterWelcomeShown`). Если появится bot cloud storage (`bots.getStorage`-аналог) — можно вернуть.
- Донаты, «Отправить подтверждение @exteraOwner», доллары/TON-курсы — заменены нашим магазином.

## 5. Что скрыто до поддержки сервером

| Без чего | Поведение клиента |
|---|---|
| `number` | нет `#N`: стрелка без гравировки, нет пилюли и подсказки над именем, подпись «Теперь вам доступно:». |
| `sg_badges_transfer=true` | кнопки передачи скрыты (нужны ещё `sg_badges_bot`, статус SUPPORTER, не developer). |
| `sg_badges_early_builds_url` | перк «Ранние сборки» и кнопка канала скрыты. |
